## 3. 既存データへの影響

- **既存リード31件は削除・統合しない。** メタデータ反映だけでは既存レコードの値は変わらない。
- 既存リードには医院IDが入っていないため、連携を有効にすると、同じ医院でも外部ID(医院ID)で別の新規リードが作られる可能性がある。対応案(要承認):
  | 区分 | 件数 | 対応案 |
  |---|---|---|
  | 確実に一致 | 1 | 既存リードへ医院IDを設定(以後はこのリードを更新) |
  | 要確認 | 3 | 担当者が確認してから医院IDを設定。確認できなければ設定しない |
  | 対応先なし | 27 | そのまま残す(19件はテスト用と思われるドメイン)。削除しない |
  - 件数はローカルDB(本番DBではない)との照合結果。**本番DBとの照合は未実施**(本番DBの読み取り手段が必要)。
  - 未ログインでの再診断により同じ医院が別の医院IDになるケースは未解決。自動統合はせず、`DentShift_Site_Domain__c`(サイトのドメイン)をSalesforceの重複ルール・レポートで確認する運用を推奨。
- 既存の商談・取引先・取引先責任者は変更しない(DENT SHIFTの外部IDを持つレコードだけを更新する)。
- 担当者がリードを取引開始(コンバート)した場合、以後の更新はコンバート先の取引先・取引先責任者へ反映し、重複作成しない。外部IDが別レコードと衝突する場合は自動統合せず、運用画面で「要確認」にする。
- 担当営業(所有者)・既存の活動・メモ・「電話お断り」の手動変更は上書きしない。新規リード作成時のみ「電話お断り(DoNotCall)」をオンにする。

| 検証 | 結果 |

| ローカル開発サーバー | 再送エンドポイントは `attempted:0`(Salesforceへ送信しない)。TimeRex Webhookは公式形式で受信・同一予約の再通知で1件・偽造参照は無視を確認 |
| メタデータ | 生成XMLの構文検証済み。**Salesforceへの検証デプロイ(checkOnly)は未実施**(本番組織への接続を伴うため承認後) |
| Salesforce実組織との結合試験 | **未実施**(Sandboxが無いため)。PGliteはDBの検証であり、Salesforceとの結合試験の代わりではない |
| TimeRexの`url_params` | 公式仕様では予約ページURLのクエリがWebhookに含まれる。**埋め込みカレンダー経由で実際に含まれるかは未確認**(テスト予約で確認する) |
| 本番の同期ログ集計 | 未実施(本番DB・ログへのアクセス手段が無い) |

テストで確認している主な要件:
- 有料契約後の解約でも商談は受注のまま。有料化せず解約した場合のみ失注(`salesforceCrmMapping.test.ts`)
- 古いStripe通知で契約期間・解約予定・トライアル日付・プランが巻き戻らない。解約通知が先に届いても初回有料化日時を記録(`tests/integration/salesforceCrmConsistency.test.ts`)
- 同じ医院の同期は医院単位のロックで直列化し、ロック取得後に読んだ最新状態だけを送る。ロックを失った同期は書き込まない(同上・`salesforceSync.test.ts`)
- メールアドレスだけで医院を統合しない。予約も医院代表メールの一致だけでは紐づけない(同上)
- 接続先組織の不一致・認証失敗では書き込まず、試行回数を消費せず、その回の再送を打ち切る(`salesforceClient.test.ts`・`salesforceSync.test.ts`)
- 再送には理由の入力を必須にし、監査ログへ実行者・日時・対象・理由を記録(`integrationEventOps*RetryRoute.test.ts`)
- アプリが送る項目がすべて項目定義・メタデータに存在する(`salesforceMetadataSpec.test.ts`)
