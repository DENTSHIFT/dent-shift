# DENT SHIFT — Security & Auth Design (P0)

## E. 認証・テナント分離設計

### 認証ドメインを2系統に分ける

1. **医院側**(院長・スタッフ・制作会社) — `contacts.role in (owner, staff, agency)`。ログイン後は自院の `clinic_id` にスコープされたデータのみ参照可能。
2. **運営側**(管理・CS・分析・経理) — 社内オペレーター。クロステナント参照が必要だが、必ず監査ログ(`audit_logs`)を残す専用経路(service role)を経由する。この権限をエンドユーザー向けAPIキーやセッションと混在させない。

### テナント分離の実装方針

- 認証基盤(Supabase Auth / Auth.js等、最終選定は未確定)のセッションから `clinic_id` を解決し、以降の全クエリに強制付与する。
- Postgres RLSを一次防御とする: `USING (clinic_id = current_setting('app.clinic_id')::uuid)` のようなポリシーを各テーブルに設定し、アプリ層のクエリ漏れがあってもDBレベルで遮断する。
- 運営側の管理画面は別route group(`app/(ops)`)とし、通常の医院向けセッションとは異なる認可チェックを通す。

### ログインと医院代表電話番号の分離

- ログインはメール+パスワード(またはメールマジックリンク)で運用する。無料診断では医院代表電話番号を必須入力として医院情報へ保存するが、患者電話番号は取得・保存しない。

## F. セキュリティ設計

### 外部書き込みの人承認ゲート

広告変更・GBP変更・医院サイト変更・口コミ返信・医療情報公開など、外部へ影響する操作は以下のワークフローを必須とする。

```
[AIが変更案を検出/生成] → [improvement_tasks に proposed として登録]
        → [人(医院担当 or 運営)がUI上で内容を確認]
        → [approved (audit_logsに承認者・日時・diffを記録)]
        → [実行]
```

`requires_external_write = true` のタスクは、承認されるまで実行エンジンが自動実行できない設計にする(フラグチェックをジョブ実行の入口で強制)。

### PIIの取り扱い

- 患者個人情報を受け取りうる入力経路(フォーム、Webhook、AI応答の転記)には、保存前のバリデーション層を設け、氏名・電話番号・メールアドレス等のパターンを検知した場合は保存せず破棄またはマスクする。
- 医院の代表連絡先(`contacts.email` 等)は患者情報ではないため区別して扱う。
- パスワードは平文保存禁止(認証基盤側のハッシュ管理に委譲)。外部APIのアクセストークンは暗号化して保存し、平文ログ出力を禁止する。

### 取得不能値の扱い

- APIエラー・未取得の値は `null` または明示的な状態(`not_configured` / `needs_reauth` / `temporarily_unavailable` / `insufficient_data` / `error`)で表現し、**0として扱わない**。
- 推定値には「推定」、mock/サンプルデータには `is_sample = true` を付与し、UI・レポート上で明示する。実績として表示しない。

### 監査・可観測性

- 承認を要する操作、決済状態変更、権限変更は全て `audit_logs` に記録する。
- APIには冪等性キー(特に決済Webhook)、認証・認可チェック、入力バリデーション、構造化エラー、レート制限、リトライ/タイムアウト、プロバイダ障害時のフォールバックを組み込む。

### 医療広告・表現チェック(P0スコープ内の最低限)

診断結果・改善提案の生成テキストが以下に該当しないかの機械チェックを、公開前のレビューフローに組み込む(最終法務判断はDENT SHIFTが行わない)。

最上級表現 / 比較優良表現 / 安全性断定 / 効果断定 / 根拠のない数字 / 費用・期間・リスクの説明不足 / 患者体験談・ビフォーアフターの無断使用 / 自費診療の要件未記載 / 口コミインセンティブ / 個人情報を含む口コミ返信

### AI生成人物の表示ルール

- 担当者プロフィールには必ず「AI生成モデル」バッジを表示し、「お問い合わせにはDENT SHIFTのCSチームが対応します」を併記する。実際の回答主体(AI/CSチーム)を偽装しない。

### 決済状態遷移(Webhook駆動)

`trial/free → active → past_due → restricted → suspended → cancel_scheduled → cancelled`

決済失敗後に即解約しない。自動再請求を行い、成功後は自動復旧する。督促電話は行わない。
