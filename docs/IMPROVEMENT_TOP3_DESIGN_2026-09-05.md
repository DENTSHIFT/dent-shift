## 1. 現在の改善TOP3仮実装の問題点

対象コード: `src/server/services/runFreeDiagnosis.ts` の `buildTopImprovements()`

1. **優先度算出が正本の4軸20点式になっていない**。実際は `impact` / `confidence` / `urgency` の3値(high/medium/low)を weight(3/2/1)で単純に掛け算しているだけで、正本§1.2の「集患インパクト・緊急性・実行容易性・波及効果」の4軸× 各5点 = 20点という設計とは無関係。`confidence` という正本にない独自軸が紛れ込んでいる一方、正本にある「実行容易性」「波及効果」は評価されていない。
2. **改善候補の生成ロジックが正本のカタログ(45項目)を反映していない**。現状は「領域の達成率が50%未満なら汎用の改善案を1件生成」という条件だけで、正本§2〜7が定義する「検出内容→生成アクション→優先度→推奨担当」の具体的な対応表(AIO7・LLMO6・MEO7・SEO7・Web予約導線10・口コミ8 = 計45項目)を一切参照していない。
3. **自動エスカレーション規則(正本§8)が未実装**。予約障害・情報不一致・計測障害・法務規約リスク・クロール障害の5分類は、スコア計算を待たず最優先で表示すべきだが、現状はそのような特別扱いが存在しない。
4. **`QuestionOutcomeStatus.insufficient_data` が実際には一度も出力されない**(`src/domain/competitor/types.ts` に型は定義済み)。`buildQuestionResults()` は観測件数が0件でも `mentionedCount === 0` として無条件に `"lose"` を返しており、「AIに聞かれていない」ことと「AIに聞かれたが選ばれなかった」ことを区別できていない。これはAIOの改善候補生成(「AIに選ばれていない質問」)の誤検知につながる。
5. **evidenceが文字列配列に平坦化されている**。`domainEvidenceSummaries()` で構造化された `CriterionEvidence`(`ruleKey`/`sourceUrl`/`observedValue` を持つ)を `summary` 文字列だけに潰しており、正本§10(制作会社向け修正指示書)が要求する「対象箇所(URL/ページ名)」「計測(イベント名・パラメータ)」への追跡可能性が失われている。
6. **TOP3以外の候補が破棄される**。`candidates.slice(0, 3)` で残りを捨てているが、正本§1.3は「TOP画面には最優先アクションを最大3件まで表示し、それ以外は領域別・担当者別・期限別に絞り込める設計とする」としており、TOP3以外の候補も保持・提供する必要がある。
7. **同点時の優先順位が未定義**。`weight[b.urgency] * weight[b.impact]` が同値の場合、`Array.prototype.sort` の安定性に依存した偶発的な順序になる。

## 3.「4軸 × 各5点 = 20点」の評価設計

正本§1.2の4軸(集患インパクト/緊急性/実行容易性/波及効果)は、各軸の「5点(満点)の状態」の定性的な説明はあるが、0〜4点の中間段階や、実データからどう機械的に算出するかは正本に定義がなく、正本自身も§12で「各検出閾値と優先度点数の実データ調整」を **Ver.1時点の「検証」項目(未確定)** として明記している。そのため以下はこのGAP分析の延長として**当セッションが提案するVer.1準拠のルーブリック案**であり、実データ運用後の再調整を前提とする。

### 3.1 各軸のスコア根拠(0〜5点、整数)

| 軸 | 0-5点の算出方法(提案) |
|---|---|
| **集患インパクト** | 検出カタログ表(正本§2〜7)の「優先度」列を起点とするベースライン(最優先=5 / 高=4 / 通常=3)。そこから、候補が属する領域の配点比率(AIO30・MEO20・SEO15・LLMO15・予約10・口コミ10のうち、当該criterionが占める割合)で ±1 調整し、さらに「予約・来院に直結する検出か」(例: 予約リンク切れ、GBP予約リンク切れ)は+1、間接的な情報整備系(例: 更新日の明記)は−1。最終的に0〜5にクリップ。 |
| **緊急性** | カタログ表の「優先度」列をベースラインとし(最優先=5 / 高=3 / 通常=2)、当該candidateが§8の自動エスカレーション条件に該当する場合は無条件で5点固定(4章参照。ただしエスカレーション対象は4章のとおりスコア計算自体をバイパスするため、この5点は「表示上の一貫性のため」の位置づけ)。 |
| **実行容易性** | カタログ表の「推奨担当」列から逆算。医院単独で完結(情報入力・文言修正等)=5、院長承認のみ追加=4、制作会社が必要だが単純作業=3、医院+制作会社など複数関係者の調整が必要=2、審査・大規模改修を伴う(例: クロール阻害の解消、テキスト化)=1。 |
| **波及効果** | その検出項目が影響する領域・criterionの数で判定。単一criterionのみに影響=1〜2、同一領域内の複数criterionに影響=3、複数領域(例: NAP情報統一はAIO/MEO/LLMOに波及)にまたがる=4〜5。 |

各軸0〜5点(整数)× 4軸で合計0〜20点。

### 3.2 表示区分(正本§1.2表そのまま採用)

| 合計点 | 表示区分 | UI上の扱い |
|---|---|---|
| 16–20 | 最優先 | TOP改善に表示 |
| 11–15 | 優先 | 早期対応 |
| 6–10 | 通常 | 改善リスト |
| 0–5 | 経過観察 | モニタリング |

## 4. 重大リスク自動エスカレーションの判定条件

正本§8の5分類をそのまま採用し、既存の診断データ構造にマッピングする。

| 分類 | 判定条件(正本) | 実データ上の検知方法(提案) | システム処理 |
|---|---|---|---|
| 予約障害 | 予約・電話・フォームが機能しない | `WEB_BOOKING`領域の `booking_funnel_flow`/`form_usability` criterionが最低点(0点)、またはWeb予約導線カタログの「予約リンク切れ・遷移先誤り」「フォーム送信エラー」検出ルールが発火 | 即時通知、最優先タスク、再テスト必須 |
| 情報不一致 | 医院基本情報・診療時間・URLが主要媒体間で矛盾 | LLMOの`info_consistency`、MEOの`gbp_basic_safety`、AIOの「医院基本情報がページごとに不一致」検出ルールが発火 | 整合タスクを生成し対象媒体を列挙 |
| 計測障害 | 予約完了など主要CVが計測不能 | `WEB_BOOKING.measurement_setup`が0点、またはWeb予約導線カタログ「CV計測がない」検出ルールが発火 | 成果判定停止を明示し設定タスク生成 |
| 法務・規約リスク | 誇大表現、個人情報、口コミインセンティブ等 | REVIEWSの`policy_risk`が0点、または口コミカタログ「返信に個人情報を含む」「誇大・根拠のない表現」「特典付き・選別型の口コミ依頼」検出ルールが発火 | 緊急表示、公開停止・確認を提案 |
| クロール障害 | 重要ページが非公開・noindex・アクセス不能 | SEOの`crawl_index`が0点、またはAIO「クロール阻害・重要情報が画像のみ」検出ルールが発火 | 技術修正と再クロール確認を要求 |

**エスカレーション対象は4軸スコアの計算をバイパスし、常にTOP3の先頭グループとして扱う**(5章のフローで詳述)。1つのcandidateが複数分類に同時該当する場合は、分類の優先順位を「予約障害 > 計測障害 > 法務・規約リスク > クロール障害 > 情報不一致」とし(集患・売上への影響が直接的な順)、表示ラベルは最上位の分類のみを採用する。

## 5. 改善候補の生成 → 採点 → TOP3選定までの処理フロー

```
1. 候補生成(catalog-based detection)
   6領域 × 正本§2〜7のカタログ(計45ルール)を、DomainScore/CriterionScore
   (取得済みの構造化データ)に対して評価し、条件に合致したものを
   ImprovementCandidate として生成する。
   ※ 現状の「達成率<50%なら汎用1件」ロジックは廃止し、カタログの
     個別ルールに置き換える。
   + unavailableなdomain(全criterionがunavailable)には、7章の
     ルールに従い専用candidateを1件生成する。
   + 質問結果(insufficient_dataを含む、7章参照)から
     「AIに選ばれていない質問」candidateを生成する。

2. 自動エスカレーション判定
   各candidateを4章の5分類と照合する。該当するものは
   escalated = true としてマークし、4軸採点をスキップする
   (表示上は緊急性=5, 他3軸は3.1のルールで採点し根拠として保持する)。

3. 4軸採点(非エスカレーション candidateのみ)
   3章のルーブリックに従い、集患インパクト/緊急性/実行容易性/波及効果を
   それぞれ0-5点で算出し、合計(0-20点)と表示区分を確定する。

4. ソート
   (a) escalated=true を先頭グループとし、グループ内は
       4章の分類優先順位 → 検出順 で安定ソート
   (b) escalated=false は合計点の降順。同点時は6章のタイブレークを適用

5. TOP3選定
   ソート済みリストの先頭3件を「TOP改善」として返す。
   残りは全件保持し、領域別/担当者別/期限別のフィルタ用に
   allImprovements として返す(既存の topImprovements フィールドは
   後方互換のため維持し、上位3件のみを引き続き格納する)。
```

## 6. 同点時の優先順位(タイブレーク)

正本に明記がないため、以下を提案する(上から順に適用、最後まで一致した場合のみ検出順=DOMAIN_ORDER順というdeterministicな最終手段を置く。乱数・非決定処理は導入しない、というdomain層の既存方針を踏襲):

1. `escalated = true` は常に `escalated = false` より上位
2. エスカレーション同士は4章の分類優先順位(予約障害 > 計測障害 > 法務・規約リスク > クロール障害 > 情報不一致)
3. 非エスカレーション同士は合計点(20点満点)の降順
4. 合計点が同点の場合、緊急性の軸点が高い方
5. さらに同点の場合、集患インパクトの軸点が高い方
6. さらに同点の場合、波及効果の軸点が高い方
7. さらに同点の場合、実行容易性の軸点が高い方(=最後は「同じ優先度なら着手が軽い方を先に」という実務上自然な基準)
8. すべて同点の場合、`DOMAIN_ORDER`(AIO→LLMO→MEO→SEO→予約導線→口コミ)の並び順

## 7. unavailable / insufficient_data の扱い

### 7.1 domain/criterionレベルの `unavailable`(既存のCriterionStatus)

現行の「該当domainが全criterion unavailable → 専用candidateを1件生成する」という設計思想は正本の絶対ルール(取得不能を0点にしない/機会損失を見逃さない)と整合するため維持する。ただし優先度は4軸採点の枠組みに乗せて計算する(現状のハードコードされたimpact="medium"等をやめる):

- 実行容易性 = 5(情報登録のみで解消するため)
- 緊急性 = 3(測定できないこと自体はリスクだが、5章のエスカレーション「クロール障害」等に該当する場合はそちらを優先)
- 集患インパクト = 当該領域の配点比率から算出(3.1と同じ式)
- 波及効果 = 2(その領域の今後の全criterion評価を可能にするという間接効果)

一部criterionのみunavailable(domain全体はpartial)な場合は、個別criterion単位でカタログの検出ルールを評価する対象から除外し(判定不能なため誤検知を避ける)、candidateを生成しない。

### 7.2 質問結果レベルの `insufficient_data`(既存のQuestionOutcomeStatus、現状未使用)

`buildQuestionResults()` を修正し、該当質問の観測件数が0件(全AIプロバイダーで観測結果を取得できなかった場合)は `"insufficient_data"` を返すようにする。判定式(提案):

```
observations.length === 0        → "insufficient_data"
mentionedCount === 0             → "lose"
mentionedCount === length &&
  bestRank <= 1                  → "win"
それ以外                          → "close"
```

`insufficient_data` の質問は「AIに選ばれていない質問」candidateの母集団(losingQuestions)から除外する。「聞かれていない」ことと「聞かれたが負けた」ことを混同しないという正本8.3章の方針(断定表現を避ける)に沿う。`insufficient_data` が一定件数以上ある場合は、それ自体を「AI観測データが不足しています」という別candidate(実行容易性=5、緊急性=2程度)として提示することを検討するが、これはP0の必須要件ではないため今回は見送り、TOP3ロジック側では「除外するだけ」に留める(過剰実装を避ける)。

## 8. evidenceとの紐付け方法

現状の `evidence: string[]`(summaryを平坦化した文字列配列)を、既存の構造化型 `CriterionEvidence`(`summary`/`ruleKey`/`sourceUrl`/`observedValue`)をそのまま再利用する形に変更する。あわせて、どのカタログルールがこのcandidateを生成したかを追跡できるよう、`ruleKey`(例: `improvement-logic:2-crawler_block`のように正本の章番号を含む識別子。`scoreCriteria.ts`の`ruleKey`命名規則に合わせる)と、影響するスコア領域(`sourceCriteria: { domain, criterionKey }[]`)をcandidate自体にも持たせる。

これにより:
- 正本§1.3「改善タスク共通データ」の「優先度と根拠」「影響するスコア領域」を満たす
- 正本§10(制作会社向け修正指示書)が要求する「対象箇所(URL等)」「計測(イベント名・パラメータ)」への変換時に、`sourceUrl`/`observedValue`から機械的に生成できる
- UIの改善は今回のスコープ外だが、将来UI側が「なぜこの点数か」を表示する際に文字列の再パースが不要になる(データ構造として引き継ぐだけで済む)

## 10. unit test方針

既存の `tests/unit/scoring.test.ts` / `tests/unit/mockScoreProvider.test.ts` のスタイル(vitest、`describe`/`it`、`DOMAIN_CRITERIA`ベースのfixtureビルダー関数)を踏襲する。

1. **`priorityScoring.test.ts`(純粋関数の境界値テスト)**
   - 4軸それぞれの算出関数を、境界値(0/3/5点になる入力)でテーブル駆動テスト
   - 合計点→表示区分の閾値境界(5/6, 10/11, 15/16点)を全パターン検証
   - エスカレーション該当時に4軸採点がバイパスされ常に先頭グループになることを検証
   - タイブレーク関数を6章の8段階すべてについて、意図した順序になることを個別ケースで検証
   - 同一入力を2回評価して結果が完全一致すること(決定性テスト。乱数混入がないことの回帰防止)

2. **`candidateCatalog.test.ts`(検出ルールの発火/非発火テスト)**
   - 45ルールそれぞれについて、「発火すべきfixture」と「発火してはいけない健全なfixture」の最低2ケース(`buildFullCriteria`/`buildUnavailableCriteria`に類する既存パターンを拡張して再利用)
   - 同一診断結果に対して重複・矛盾する候補が生成されないこと(例: unavailable domainから個別criterionルールが誤発火しないこと、7.1節の除外ロジック)

3. **`runFreeDiagnosis.test.ts`(結合レベル)**
   - `topImprovements` が常に3件以下であること
